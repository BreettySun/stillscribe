# 模型服务解耦：让用户在设置里自选模型 — 设计文档

> 日期：2026-11-18　状态：已批准（2026-11-18，含第 4 节对铁律 #6 的修改）
> 配套：`CLAUDE.md`、《视频生成文章-架构文档》、《视频生成文章-AI集成》、`shared/types.ts`
> 本文档**修改一条已决策的铁律（#6 的出站范围）**，见第 4 节，需项目负责人确认。

---

## 1. 意图与原因

现在全自动写文章（M7）只能用 Google Gemini：SDK、结构定义、配置项、Key 文件名、界面文案都写死了 Gemini，Key 还要靠往磁盘丢明文文件来配置。

目标：**最终用户能在应用的设置里自由选择合适的模型，不被锁死在 Gemini。** 用户自己填服务地址、自己的 Key、模型名，保存后全自动流程就用它。

## 2. 目标 / 非目标 / 反目标

**目标**

- 设置界面里可配置：接口地址、API Key、模型名、喂图方式；可"测试连接"。
- 引擎只用一种通用接口格式（OpenAI 兼容的 `chat/completions`）调用模型，不依赖任何厂商 SDK。
- 现有 Gemini 用户升级后**无需任何操作**就能继续用（Key 自动迁移，默认地址指向 Gemini）。
- 代码、契约、环境变量、界面文案的命名全部改为与厂商无关。

**非目标（本次不做）**

- 多套配置档案的管理界面（命名、列表、切换）。本次只有"一套当前配置"，但 Key 按地址分别记住（见 5.3）。
- 每个任务单独选模型。配置是全局的。
- 自动拉取服务端的模型列表。模型名手填。
- 为任何厂商写原生适配器。
- 针对图片数量 / 请求体积上限的自动分批。超限时按现有机制失败并降级半自动。
- 修改喂图方式的默认值（仍为 `grids`）。只是把它做成可选项，见第 9 节。
- 重写提示词。沿用同一份模板（`CLAUDE.md` §8）。

**反目标（出现即视为失败）**

- 某个地址的 Key 被发往另一个地址。
- Key 明文可被渲染进程读回、写进日志 / URL / SQLite / 仓库 / 导出文件。
- 现有 Gemini 用户升级后全自动失效。
- 半自动模式或下游（校对、换图、M8 导出）的行为发生变化。

## 3. 做法的选择（Approaches）

| 方案 | 内容 | 取舍 |
|---|---|---|
| 一 | 保留 Gemini 原生客户端，另加一个通用兼容接口适配器 | 现有路径不动，但要维护两套结构定义和"供应商"概念 |
| 二 | 每家厂商一个原生适配器，下拉里是固定名单 | 每家效果最可控；但名单之外用不了，每加一家要发版，与"自由选择"相悖 |
| **三（已选）** | 只保留通用兼容接口，Gemini 也走它；去掉 `@google/genai` | 一条代码路径、无厂商 SDK、设置最简单；代价是 Gemini 走 Google 标注为 beta 的兼容层 |

没有列入的做法：引入统一的多厂商 SDK——会带进一整套新依赖，与 `CLAUDE.md` §2"技术栈锁定"冲突。

**选三的依据是一次实测**（2026-11-18，一次性脚本，未提交）：同一个 5 分钟视频的真实素材（3 张宫格图 + 字幕 + 正式提示词），`gemini-2.5-flash`，两条通道各约 10 轮。

| | 兼容接口 | 原生接口 |
|---|---|---|
| 产出合格 Article JSON | 10 / 10 | 9 / 9 |
| 配图时间戳非法的轮次 | 1（12 页里 6 页把 `00_01_00` 写成 `01_00_00`） | 0 |
| 正文混入中文 / notes 缺失 | 0 / 0 | 0 / 0 |
| 单次耗时 | 49–61 秒 | 49–64 秒 |
| 图片 token 计费 | 相同 | 相同 |
| 单帧模式（115 张 webp，一次请求） | 通过 | 通过 |
| 连接被对端断开（并发 6 个请求时） | 4 次 | 1 次 |

实测还给出两条设计约束：

1. **不带强制结构时不可靠**：只靠提示词约束的 2 轮里，1 轮返回非法 JSON，1 轮包在 ```` ```json ```` 代码块里。所以强制结构是首选，"只靠提示词"只是最后退路。
2. **网络层断连两边都会发生**，必须靠重试覆盖（现有 M7 已有 2 次重试）。

实测未覆盖：长视频、Gemini 以外的任何服务。

## 5. 设计

### 5.1 整体数据流

```
设置界面 ──(HTTP)──▶ 引擎 /settings/ai        地址、模型、喂图方式 → SQLite
设置界面 ──(IPC)───▶ Electron 主进程           Key → safeStorage 加密落盘
                       └──(HTTP，带引擎令牌)──▶ 引擎 /settings/ai/key   Key → 仅内存
M7 ──▶ 读当前配置 + 取该地址的 Key ──▶ 通用客户端 ──▶ {地址}/chat/completions
```

- 非机密配置归引擎 + SQLite（铁律 #9）。
- Key 的持久化仍归 Electron 主进程的 `safeStorage`（与《AI集成》§4 既定方案一致）；引擎保持与 Electron 无关，只在内存里持有 Key。
- 渲染进程访问引擎仍只走 HTTP；IPC 只用于"把 Key 交给主进程"，不直连引擎（铁律 #8）。

### 5.2 通用客户端（引擎）

替换 `engine/src/modules/m7/geminiClient.ts`。对外接口保持现在的形状（图片 + 字幕 + 提示词 → `Article`），只是改成中立命名；`index.ts`、`pipeline.ts` 仍然只认这个接口。

需要改动的接线：现在 `queue.ts` 和 `run.ts` 是直接调 `resolveAIConfig()`（纯读环境变量）再构造客户端，`Orchestrator` 拿不到 `SettingsStore`。本次要让"取当前配置 + 取该地址的 Key"成为一个可注入的依赖：`serve.ts` 把基于 SQLite 设置和内存 Key 表的实现传给 `Orchestrator`；`run.ts` 传只读环境变量的实现。配置在每个任务进入 M7 时现取，这样运行中改设置能对下一个任务生效。

- 请求：`POST {baseUrl}/chat/completions`，用 Node 自带 `fetch`，**不引入 SDK**。
- 消息：一条 `user` 消息，内容依次为提示词文本、字幕文本、各图片（`image_url`，值为 `data:<mime>;base64,...`）。与现在发给 Gemini 的顺序一致。
- Key：只放 `Authorization: Bearer <key>` 请求头。没有 Key 时不带该请求头（本机模型）。
- 超时：单次请求 300 秒。
- 重试：沿用 `index.ts` 现有的重试（默认 2 次），不在客户端里另加一层。

**结构化输出的三级退路**，从高到低：

1. `response_format: { type: "json_schema", json_schema: { name, schema } }`，不使用 `strict`。
2. `response_format: { type: "json_object" }`。
3. 不带 `response_format`，只靠提示词。

规则：

- 从该（地址, 模型）已记住的级别开始；没有记录则从第 1 级开始。
- **仅当**服务端以 400 / 422 拒绝请求时降一级重试；401 / 403 / 404 / 429 / 5xx / 网络错误不降级。
- 降级后成功，则把新级别记到 SQLite，下次直接用。
- 各级都以 400 / 422 失败时，向上报告**第一次**失败的服务端原文，而不是最后一次。
- 注意状态码不可全信：已实测 Gemini 兼容层对无效 Key 返回的是 **400**（`"Please pass a valid API key"`），不是 401。所以 400 的响应要先看内容是否属于鉴权 / 配置类错误，是则不降级、直接按配置错误报告。
- 无论哪一级，返回内容都经现有 `parseAndValidateArticle` 校验（它已能剥掉代码块围栏）。

**结构定义**：`schema.ts` 改写为标准 JSON Schema（小写 `type`），全项目只留这一份，内容仍镜像 `shared/types.ts` 的 `Article`。

**错误信息**要让用户看得懂并知道改哪里，至少区分：Key 无效（401/403，以及内容表明是 Key 问题的 400）、地址或模型名不对（404）、被限流（429）、服务端拒绝了请求内容（400/422，附服务端原文的前几百字符）、连不上。错误信息里不得包含 Key。

### 5.3 配置与 Key

**配置项**（存 SQLite 的 `kv_settings`）：

| 项 | 说明 | 默认 |
|---|---|---|
| 接口地址 `baseUrl` | 到 `/chat/completions` 之前的部分 | `https://generativelanguage.googleapis.com/v1beta/openai` |
| 模型 `model` | 任意字符串，手填 | `gemini-2.5-flash` |
| 喂图方式 `imageSource` | `grids` / `frames` | `grids` |
| 结构化级别 | 按（地址, 模型）记录，由程序维护，用户不直接编辑 | 无 |

取值优先级：用户在设置里保存的值 > 环境变量 > 代码默认值。命令行入口 `run.ts` 没有设置界面，只读环境变量和默认值。

**地址规范化与校验**（引擎、主进程、界面必须共用同一份实现，不得各写一份）：

- 去首尾空白、去结尾的 `/`。
- 必须是合法 URL，协议为 `https`；`http` 只允许回环地址（`localhost`、`127.0.0.1`、`[::1]`），用于本机模型。
- 不合法则拒绝保存（HTTP 400），并在界面上提示。

**Key 与地址绑定**（防止 Key 被发到别的服务）：

- Key 按规范化后的地址分别保存，是一张"地址 → Key"的表。
- 引擎发请求时只取**当前地址**对应的 Key；改了地址而新地址没有 Key，就视为未配置。
- 用户切回之前用过的地址时，之前的 Key 自动可用，不必重填。
- Key 何时必填：回环地址可以不填；其他地址必须有 Key 才算"已就绪"。

**Key 的保存（桌面应用）**：

- 文件：`userData/ai-keys.enc`，内容是整张表经 `safeStorage` 加密后的结果。
- 引擎启动时，主进程把解密后的表经环境变量 `STILLSCRIBE_AI_KEYS`（JSON）注入，沿用现在注入单个 Key 的套路；引擎崩溃重启时同样注入当前的表。
- 运行中新增 / 修改 / 清除 Key：渲染进程经 preload 新增的 IPC 把（地址, Key）交给主进程 → 主进程更新加密文件 → 主进程调引擎的 `PUT /settings/ai/key`，立即生效，无需重启。
- `safeStorage` 不可用时：不落盘，本次会话仍推给引擎，并让界面提示"Key 未能保存，重启后需重填"。

**旧数据迁移**（保证现有用户零操作）：

- 存在 `gemini-key.enc`：解密后以 Gemini 默认地址为键并入新表，写入 `ai-keys.enc` 成功后删除旧文件。
- 存在明文投放文件 `gemini-key.txt`：同上并入后删除。今后不再需要这种投放方式，README 相应改写。

**同一地址有多个 Key 来源时的优先级**：

- 表里的 Key（主进程注入的 `STILLSCRIBE_AI_KEYS`，以及运行中经 `PUT /settings/ai/key` 写入的）优先于环境变量里的单个 Key。
- 界面上的"清除"只删表里的条目。若环境变量里还有该地址的 Key，它继续生效，界面显示"来自 engine/.env"且不提供清除按钮。

**三种运行形态**：

| 形态 | Key 的保存 | Key 输入框 |
|---|---|---|
| 打包后的桌面应用 | `safeStorage` + `ai-keys.enc` | 可用 |
| Electron 开发态（未打包） | 与打包后相同（落在开发用的 userData 下），便于在开发态验证整条链路；现有 `apiKey.ts` 里"未打包直接返回"的短路去掉 | 可用 |
| 纯 Web 开发模式（无 Electron） | 只来自 `engine/.env` | 禁用，提示"开发模式下 Key 在 engine/.env 配置" |

三种形态下地址、模型、喂图方式都照常可改。

**环境变量**（开发期）：

| 新 | 说明 |
|---|---|
| `STILLSCRIBE_AI_BASE_URL` | 接口地址 |
| `STILLSCRIBE_AI_API_KEY` | 属于 `STILLSCRIBE_AI_BASE_URL`（未设则属于默认地址）的 Key |
| `STILLSCRIBE_AI_MODEL` | 模型 |
| `STILLSCRIBE_AI_IMAGE_SOURCE` | 不变 |
| `STILLSCRIBE_AI_KEYS` | 仅供主进程向引擎注入整张表 |

旧变量 `STILLSCRIBE_GEMINI_API_KEY`（视为 Gemini 默认地址的 Key）和 `STILLSCRIBE_GEMINI_MODEL` 继续被读取，作为兜底，`.env.example` 里标注为已弃用。

### 5.5 测试连接

用当前已保存的配置发一次小请求，回答用户三个问题：连得上吗、模型能看图吗、能稳定输出 JSON 吗。

- 分两步，先易后难，这样配置错误不会被误报成"不支持某功能"：
  1. 只发一句纯文本、不带图片、不带强制格式。这一步失败一律按配置错误（地址 / Key / 模型名）报告，附服务端原文。
  2. 通过后再发：一句简短提示词 + 一张**写死在代码里的纯色小图常量**（不在运行时编码图片，铁律 #2），要求模型按结构返回并说出图片颜色，同时按 5.2 的退路探测结构化级别。
- 结果包含：是否成功、能否看图（颜色答对）、最终用上的结构化级别、耗时、失败时的可读原因。
- 测得的结构化级别顺手记到 SQLite（即 5.2 里"已记住的级别"）。
- 界面对三种级别的说明：`json_schema` → "支持强制结构"；`json_object` → "仅保证是 JSON"；无 → "不支持强制输出格式，生成可能偶尔失败并转为人工回填"。
- 不能看图时明确提示"该模型无法识别图片，不适合本应用"，但不阻止保存。

### 5.7 全自动失败时让用户看到原因

现状：全自动失败后任务静默降级为半自动，原因只写在引擎的 stderr 里。以前只有一家服务、配置由开发者管，这没问题；现在用户自己填地址和模型，失败会常见得多，静默降级会让人不明白"我选了自动，为什么要我手动粘贴"。

- 引擎：降级时把可读原因（5.2 的错误信息）记到任务上（5.4 的新字段）；之后该任务成功得到文章（重新生成或人工回填）时清掉。
- 界面：校对页在"没有文章草稿且有这条原因"时，显示一条不阻断操作的提示，内容为原因本身加一句"可以在下方手动回填，或到设置里检查模型配置"。
- 降级行为本身不变：任务不失败，仍进入待校对。

- 失败兜底：缺配置 / 调用失败不让任务失败，降级到半自动校对界面。
- 铁律 #4：中文说明只进 `notes`。
- 半自动模式、M8 导出、提示词模板及其打包方式。

## 7. 验收标准

1. 全新安装：打开设置，默认是 Gemini 预设；填入 Key，"保存并测试"通过；提交一个 `auto` 任务能生成文章草稿并进入校对。
2. 升级安装（已有 `gemini-key.enc`）：不做任何操作，`auto` 任务照常工作；旧文件已被迁移并删除。
3. 改用"自定义"地址并填入另一把 Key：之后的请求只带新 Key 发往新地址；切回 Gemini 预设，原 Key 仍可用。
4. 改了地址但没填该地址的 Key（非回环）：`ready` 为 false，`auto` 不可选。
5. 运行中修改配置：无需重启应用，下一个进入 M7 的任务即使用新配置。
6. 对不支持 `json_schema` 的服务：自动降级并记住，后续请求不再先撞一次 400。
7. Key 不出现在：任何 HTTP 响应、日志、SQLite、URL、渲染进程可读的状态里。
8. `engine` 的依赖里没有任何厂商 SDK；全仓库除文档里的历史说明和默认预设外，不再有以 Gemini 命名的代码标识符、环境变量（旧变量的兜底读取除外）和界面文案。
9. 纯 Web 开发模式下，`engine/.env` 里配置的 Key 仍可用，设置界面的其余项可改。
10. 故意填错 Key 或模型名：测试连接报告的是配置错误（而不是"不支持强制结构"）；提交 `auto` 任务后进入待校对，校对页能看到失败原因。

## 8. 测试要求

- 客户端：用本地起的假 HTTP 服务断言——请求形状、Key 只在请求头且不在 URL、无 Key 时不带请求头、三级退路的降级条件（400/422 降，401/404/429/5xx 不降）、各类错误的可读信息里不含 Key。
- 地址规范化与校验：`https` 通过、非回环 `http` 拒绝、回环 `http` 通过、结尾斜杠归一。
- 设置路由：保存 / 读取 / 非法值 400；`PUT /settings/ai/key` 不回传 Key；三条新路由未带令牌时 401。
- Key 表与地址绑定：地址 A 的 Key 不会被用于地址 B。
- 旧 Key 迁移：把迁移逻辑写成不依赖 Electron 的纯函数来测。
- 现有 M7 测试（替身客户端）改名后继续通过。
- 真实调用：通用冒烟脚本对 Gemini 兼容地址跑通一次。

## 9. 已知风险与后续

- **宫格图模式的配图集中在视频开头**。实测约 190 页配图里没有一页选自最后一张宫格图，两条通道都如此；单帧模式能覆盖全片（各只跑了 1 轮）。这与接口无关。本次只把喂图方式做成可选项；是否把默认改为单帧需要多视频评估（单帧的输入 token 约为宫格图的 9 倍，长视频的图片数可能超出部分服务的上限），另行处理。
- **提示词是针对 Gemini 调的**，换其他模型的文章质量没有保证，也没有测过。
- **Gemini 的兼容层被 Google 标注为 beta**。客户端接口保持不变，日后若有必要可以补回一个原生适配器，只是加一个文件。
- **"兼容"不是严格标准**，各家在图片格式、单次图片数、报错格式上可能有出入，只能在用户实际使用和"测试连接"中暴露。

## 10. 留给实现者决定的事

文件与标识符的具体命名、对话框内的布局细节与文案措辞、错误信息的具体措辞、测试的组织方式、判定"服务端拒绝了 `response_format`"之外是否需要更细的降级判据、迁移与注入的代码组织。

## 11. 由设计者做出的决定（负责人未明确要求，审阅时请留意）

1. Key 按地址分别保存，而不是全局只存一把（为了防止 Key 被发到别的服务，顺带免去切换时重填）。
2. 非本机地址必须是 `https`；`http` 只允许回环地址。局域网内用 `http` 提供服务的模型本次不支持。
3. 本机（回环）地址可以不填 Key。
4. 预设只放 Google Gemini 和"自定义"，其他服务实测通过后再加。
5. 喂图方式做成可选项，但默认值不变（仍是宫格图）。
6. 全自动失败的原因要在校对页显示给用户（5.7），为此给 `Task` 加了一个字段。
7. Electron 开发态启用与打包后相同的 Key 保存链路（原来是关闭的）。
8. 环境变量里的旧名字继续可用，作为兜底。
9. 纯 Web 开发模式下不能在界面里填 Key。

## 12. 实施后的修订（2026-11-18）

整分支审阅后按实现修订如下，前文各节保留原样，以本节为准：

- **§5.3 / §5.4**：`AISettings` 不再给"已有 Key 的地址列表"，改为按地址给出 Key 来源 `keySources: Record<string, "saved" | "env">`（同一地址表与环境变量都有时为 `"saved"`）。对话框据此对任意地址显示"已保存 / 来自 engine/.env / 未设置"，"清除"只对 `"saved"` 且能写 Key 的形态出现。
- **§5.5**："测试连接"总是从 `json_schema` 起步探测结构化级别，并用测得的结果覆盖已记住的级别（一次偶发的 400 造成的降级可借此恢复）。
- **§5.3**：未打包的 Electron 开发态使用独立的 userData 目录 `stillscribe-dev`（命令行显式传 `--user-data-dir` 时以其为准），不与打包版共用文件。
- **§5.2**：客户端不跟随重定向；任何 3xx 按配置错误报告（"地址发生了重定向，请填写最终地址"），不发第二次请求。
- **§5.2**：任务被取消时中止进行中的模型请求（错误类别 `aborted`，不重试），任务落 `canceled`，不写失败原因、不降级到半自动。
- **§5.3**：调用外部 CLI（yt-dlp 及其拉起的 deno、ffmpeg / ffprobe）时，从子进程环境中去掉模型服务 Key（`STILLSCRIBE_AI_KEYS`、`STILLSCRIBE_AI_API_KEY`、`STILLSCRIBE_GEMINI_API_KEY`）与引擎令牌 `STILLSCRIBE_TOKEN`。
- **§5.3**：无法读取的 `ai-keys.enc`（解密失败、内容非法，或加载时加密不可用）在写入新文件前改名保留为 `ai-keys.enc.unreadable-<ts>`，绝不直接覆盖。
- **§8**：Key 文件的加载 / 迁移 / 写入决策是 `shared/ai.ts` 里的纯函数（`planKeyLoad`、`decodeKeyFile`、`planKeySave`），有逐分支单测；`electron/src/main/aiKeys.ts` 只做 I/O。
- §5.2（实测后补，2026-11-18）：模型给的 `image` 不是合法帧时，先按水印的常见写法确定性纠正（最常见的是把水印 `HH:MM:SS.mmm` 错写成"分_秒_毫秒"），候选值必须是确实存在的帧才采用；还原不出来的才标记待人工换图。该现象在兼容接口与原生接口上都会出现，与本次解耦无关。实现见 `engine/src/modules/m7/timestamps.ts`。
