# 视频生成图文文章工具 — Google 登录准入方案

> 配套：《视频生成文章-架构文档》v0.5、《前端架构》、`CLAUDE.md`
> 范围：app 首次启动的**登录拦截（准入门禁）**——限定只有组织成员能用。

---

## 0. 定位与边界

- **目的**：轻门禁——限定**只有你们组织 Google 账号**能用这个内部工具，挡住组织外的人随手使用 / 防外传。
- **形态**：轻门禁 + 限定组织域 + 登录一次记住。**不需要自建后端。**
- **强度定性**：**防君子不防小人**（详见第 1 节）。这是"礼貌性门禁"，不是安全边界。对内部工具足够。
- **三条边界**（避免与其他议题缠在一起）：
  1. 这道登录只管**准入**，**不碰更新源**（更新源仍走公开 bucket，与登录无关）。
  2. **不碰 Gemini 凭证**——Google 登录只给"用户是谁"，凭证另行管理。
  3. 它是流水线（M2~M9）**之前的一道开闸**，与处理逻辑解耦。

---

## 1. 门禁强度：防君子不防小人

纯客户端校验（客户端自己检查自己放行）**原则上能被有技术的人绕过**，因为代码和数据都在用户手里：

- **改源码 / 重打包**：Electron 的 `app.asar` 解包即可读 JS，把"校验域名"的判断改成恒真或删掉拦截再打包——这是 Electron 最易被绕的点。
- **篡改本地登录态**：若登录态是个裸标记（`loggedIn: true`），用户直接改成已登录即可。
- **拦截 / 伪造网络响应**：抓包把"非组织域"改成"组织域"，或拦掉校验直接返回通过。
- **运行时 Hook**：挂钩篡改校验函数返回值，连重打包都省。

**真正防绕过只有一条路**：把校验放到用户控制不了的**服务端**，关键操作每次服务端验身份才给结果——但那是"带后端"的强准入档，本项目明确不需要。

**本项目的现实结论**：威胁模型是"防组织外随手用 / 防外传"，不是"防内部高手破解"。纯客户端轻门禁够用；底线是把**登录态做成可验证凭证**（而非裸标记），挡住"改个标记就进"这种最低级绕过，即达到合理的"防君子"强度。

---

## 2. 登录流程（OAuth + PKCE，限定组织域）

```
首次启动 → 登录页拦截 → 点"用 Google 登录"
  → 应用内独立授权窗口加载 Google 官方登录页（PKCE 流程）
  → 回调拿到 ID token / 用户信息
  → 校验：token 签名有效 且 hd/email 属于组织域
      ├─ 是 → 记住登录态（safeStorage）→ 放行进主界面
      └─ 否 → 拒绝，停在登录页（提示"仅限组织账号"）
以后启动 → 检测到有效登录态 → 直接进主界面（不再拦）
```

关键点：

1. **PKCE，不用 client_secret**：桌面 app 藏不住 secret（同 API Key 道理），走 OAuth 的 PKCE 流程——这是 Google 对"无法保密客户端"的标准做法，不需存任何机密。
2. **限定组织域**：授权时带 `hd=<组织域>` 提示只让该域登录；但 `hd` 参数可被绕，**真正校验在拿到 ID token 后**——验证 **token 签名** + 读 `hd`/`email` 确认属于组织域。此步在主进程/引擎做，不在渲染进程。
3. **登录态可验证**：记住的不是裸 `loggedIn` 标记，而是**可验证的凭证**（如校验过的 token / 加密的登录态），避免"伪造标记即进"。

---

## 3. 登录交互：尽量不开外部浏览器

诉求是"全程在软件内"。方案按推荐度：

| 方案 | 说明 | 取舍 |
|---|---|---|
| **B 应用内独立授权窗口（主选）** | 用一个独立 `BrowserWindow` 加载 **Google 官方登录页**，用户在窗口内登录，完成后回调交给 app | 视觉上不跳外部浏览器；**窗口须安全隔离**（独立 session、`nodeIntegration:false`，只承载官方页） |
| A 系统浏览器 + 回调（后路） | 调默认浏览器登录再跳回 app（OAuth 官方推荐 AppAuth 模式） | 最安全、最不易被 Google 风控，但会"跳出去开浏览器" |
| C 自建登录表单（禁止） | 在自己界面收 Google 账号密码代登 | **钓鱼式、违反 Google 条款、暴露用户凭证——绝不做** |

**结论**：主用 **方案 B**（应用内独立授权窗口）达成"不开外部浏览器"；但要：
- 该窗口**只承载 Google 官方登录页**、保持安全隔离，绝不把登录表单做进自己界面；
- 留好**回退到方案 A** 的后路——Google 出于防钓鱼会屏蔽部分"嵌入式 webview"里的 OAuth，方案 B 有被判为不安全环境而拒登的风险，需实测，不行则降级 A。

## 4. 离线策略：宽松（推荐）

"登录一次记住"的边界——记住的登录态要不要每次联网复验：

- **宽松（推荐）**：首次登录后，只要本地有有效登录态就放行，**之后不强制联网复验**。断网也能开 app（下载/处理本就联网，但 app 本身能启动），符合"轻门禁、防君子"定位。
- 严格：每次启动联网刷新 token、复验域——更"准入感"，但断网打不开，体验差。

本项目取**宽松**，不为门禁牺牲离线可用性。

---

## 5. 职责分层与安全

- **登录页 UI**：渲染进程（Vue）——只负责"点登录"和展示状态。
- **OAuth 流程 / token 校验 / 安全存储**：主进程（或引擎侧）——渲染进程**拿不到 token 明文**，符合 `contextIsolation:true` / `nodeIntegration:false`。
- **token 存储**：refresh token / 登录态用 **Electron `safeStorage`** 加密存；**绝不明文落盘、不进 git、不写 URL**（与全局密钥规则一致）。
- **授权窗口隔离**：独立 session，不开 nodeIntegration，只加载 Google 官方页。

## 6. 在架构中的位置

```
app 启动
  → [登录准入门禁] ← 本文档
       通过 → 进入主界面（Electron + Vue）
              → 提交任务 → 引擎流水线 M2~M9
       不通过 → 停在登录页
```

它是流水线之前的"开闸"，独立于 M2~M9；与更新源、Gemini 凭证均无耦合。

## 7. 实现要点清单

- [ ] Google Cloud Console 建 OAuth 客户端（桌面/PKCE 类型），配置回调方式。
- [ ] 选定回调接法：**本地回环端口 `http://127.0.0.1:<port>`（推荐，最通用）** 或自定义协议 `diggo-press://callback`。
- [ ] 主进程实现 PKCE 授权流程 + 独立授权窗口（方案 B），保留方案 A 回退。
- [ ] ID token 校验：验签 + `hd`/`email` 限组织域。
- [ ] 登录态：可验证凭证，经 safeStorage 存；启动时判断是否已登录。
- [ ] 登录页 UI + 拒绝态提示（"仅限组织账号"）。
- [ ] 退出登录入口（清除本地登录态）。

---

## 8. 待确认项

- **回调方式**：本地回环端口（推荐）vs 自定义协议——影响 Google Console 配置。
- **方案 B 可行性**：Google 是否允许该嵌入式授权环境，需实测；不行则回退方案 A。
- **是否加人员白名单**：当前是"组织域内皆可"；若要更细（仅特定成员），需一个存名单的地方（可能引入轻量云端配置，超出纯客户端范围）。
- **登录态有效期**：永久记住 vs 设过期需重登（当前默认永久记住 + 宽松离线）。
