# 视频生成图文文章工具 — 飞书导入方案（M9）

> 配套：《视频生成文章-架构文档》v0.5、《AI 集成》、《前端架构》、`shared/types.ts`
> 范围：引擎 **M9「发布」** 中，把成品一键导入飞书并得到可在线协作的飞书文档。

---

## 0. 结论先行

- **走方案 2：docx 导入**——把 M8 生成的 docx 提交给飞书导入接口，转成飞书**在线文档**（可协作），而非附件。
- 已实测验证：**图片与段落位置关系正确**，docx 导入保真足够；唯一需调整的是标题层级（见第 3 节）。
- **不为"省掉 docx 中间格式"而改走逐块构建（方案 3）**：方案 3 要重写一套块级 API + 图片单独上传，还得自己解决 docx 已经帮忙保住的图文位置关系，投入产出不划算。docx 这个**格式**保留。
- 但 docx **文件可以不落盘**：M8 用 `Packer` 出 buffer，直接喂飞书上传，省掉临时文件（可选同时落盘留底）。

---

## 1. 核心流程

```
M8 docx(dolanmiu)
  → Packer.toBuffer(doc)            // 内存 buffer，不强制写磁盘
  →（可选）落盘 article_final.docx   // 仅作本地留底/下载
  → 飞书：上传素材/云空间（用 buffer）
  → 飞书：提交导入任务（docx → 在线文档）
  → 飞书：轮询任务结果（异步）
  → 拿到新文档 token/链接
  → 回传 UI（ResultView「在飞书中打开」）
```

要点：飞书导入接口要的是 **docx 的二进制内容**，不在乎它是否在磁盘上存过文件。所以 `Packer.toBuffer()` 的 buffer 可直接进上传，**无需先写 `article_final.docx`**。是否同时落盘留底按需决定（用户若要本地 docx 下载则落盘）。

---

## 2. M8 输出约定（buffer 优先）

```ts
import { Packer } from "docx";
// const doc = buildArticleDoc(article)  // 由 M7 的 Article JSON 构建

const buffer = await Packer.toBuffer(doc);   // 内存 buffer
// 可选：落盘留底
// await fs.writeFile(path.join(workDir, "article", "article_final.docx"), buffer);

// 直接把 buffer 交给 M9 飞书上传
await feishu.importDocx(buffer, { fileName: `${videoTitle}.docx` });
```

- M8 默认产出 buffer；落盘是可选分支（留底/本地下载时才写）。
- 一份 buffer 两用：既当飞书导入源，也可写成本地 docx。

---

## 3. 标题层级约定（H4）

- 现状：docx 里小标题是 **H2**，导入飞书后也是 H2；目标是 **H4**。
- **改源头 M8**，让小标题直接生成为 Heading 4，飞书导入后自然是 H4（一次改对、每篇都对，不做导入后手动调）：

```ts
new Paragraph({
  text: page.subhead,               // 纯文本内容
  heading: HeadingLevel.HEADING_4,  // 原 HEADING_2 → HEADING_4
})
```

- 配套约定：`page.subhead` / `page.body` 是**纯文本**，不含 `##`、序号、加粗等标记；**格式一律由 M8 的 Heading 级别表达**。M7（Gemini）应只返回标题文字本身，prompt/校验里清掉混入的 `##` 或序号。
- 若将来文档出现多级标题（主标题等），需整体规划层级避免断层（如 H1 直接跳 H4）；当前只有小标题这一层级，H4 即可。

---

## 4. 鉴权（前置，一次性）

- 在**飞书开放平台**创建**企业自建应用**，拿 `app_id` / `app_secret`，开通权限：云空间（drive）上传、文档导入、上传素材等。
- 调任何接口前先换取 **access token**。
- **凭证安全**（与全局密钥规则一致）：`app_secret`、token 只存**引擎本地 / 安全存储（safeStorage）**，**绝不进渲染进程、不进 git、不写 URL/query**。调用全部在引擎完成，渲染进程只触发动作、拿回链接。

---

## 5. 目标空间与 token 选型

文档创建在哪，决定用哪种 token：

| 方案 | token | 说明 | 适配 |
|---|---|---|---|
| **统一团队知识库/文件夹** | tenant token（应用身份） | 所有产出汇到一处，无需用户逐个授权 | **推荐（内部工具）** |
| 各自个人空间 | user token（需 OAuth 用户授权） | "导进我自己的飞书"，但要引入用户授权流程，更重 | 暂不 |

**建议**：内部工具用**统一团队知识库 + tenant token**，落地最快、免用户授权。把目标文件夹/知识库 ID 作为配置项。

---

## 6. 实现步骤（方案 2，引擎 M9）

1. **换 token**：取 tenant access token（引擎本地缓存，注意有效期与刷新）。
2. **上传**：把 M8 的 docx buffer 通过云空间/素材上传接口传上去，拿到文件标识。
3. **提交导入任务**：调导入接口，指定：源为 docx、目标类型为飞书在线文档、目标位置（团队知识库/文件夹）。
4. **轮询结果**：导入是**异步任务**，用返回的 ticket 轮询，直到拿到新文档 token/链接（轮询要设超时与重试）。
5. **回传 UI**：把飞书文档链接回传，任务标完成；ResultView 显示「在飞书中打开」可点击链接。

> 异步轮询期间，按已有的 `EngineEvent` 机制给 UI 推进度/状态（如「导入中」）。

---

## 7. 失败与边界

- 上传/导入/轮询任一步失败：重试有限次，仍失败则把错误回传 UI，并保留本地 docx（若已落盘）作为兜底，用户可手动导入飞书。
- token 过期：自动重新换取后重试。
- 大文件/图片多：注意接口体积与超时限制（实测确认）。
- 标题/排版若飞书侧仍有细微样式差异：优先回 M8 调（源头），而非每篇手改。

---

## 8. 与其他模块的关系

- **输入**来自 M8（docx buffer）；M8 的 docx 由 M7 的 `Article` JSON 构建。
- **M9** 是「发布」环节，飞书导入是其一种目标（另有本地 docx 导出）。
- 凭证管理与《AI 集成》里 Gemini Key 同属"密钥只在引擎本地"的统一规则。
